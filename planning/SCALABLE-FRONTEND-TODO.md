# Scalable Frontend TODO

This backlog records the next design and architecture steps required as PERL grows beyond the current mock-sized school data. It complements `planning/PLAN.md`; it does not change the phase order in `CLAUDE.md`.

## Current UI contracts

- Routed screens live in `src/pages/`, composed reusable sections live in `src/modules/`, and atomic reusable UI lives in `src/components/`.
- Full record collections use the shared `Pagination` component. Small dashboard and live-monitor collections are explicitly bounded previews and link to a full paginated screen.
- Create and edit actions from record lists open in the shared `Modal` component. A dedicated settings page can keep a single settings form inline when it is the page's only task.
- Primary application destinations live in the hamburger navigation drawer.

- [ ] Add a component catalog such as Storybook for shared primitives and modules, including representative school themes and long-content states. (Deferred: one developer, pre-launch, no second consumer of the component API yet to disagree about it. Trigger: a second frontend developer joins, or a shared component's contract becomes a recurring source of confusion/regressions.)
- [ ] Add focused interaction and accessibility tests for reusable components with meaningful behavior; avoid snapshot-only coverage. (Deferred: this frontend has zero test-runner infrastructure today (`package.json` scripts are only `dev`/`build`/`lint`/`preview`) — adding coverage for the new reusable components (`ConfirmDialog`, `UserForm`, `InlineAlert`) would mean standing up a whole test framework first, which is its own infra decision, not a one-line addition. Trigger: introducing vitest/playwright for another reason, or a reusable component regressing in a way manual QA missed.)
- [ ] Add visual regression coverage for the live attendance stage, modal editors, pagination, and navigation drawer at agreed desktop and mobile viewports. (Deferred: same reasoning as above, plus no visual-regression tool wired in. Trigger: multiple people touching shared CSS/components concurrently, where regressions stop being catchable by a single owner's manual review.)
- [ ] Prepare localization-safe copy, date/time formatting, and layouts for longer translated labels. (Deferred: product is English-only for the Philippine market today (`timezone` defaults to Asia/Manila, DepEd school ID field, RA 10173 compliance work is English-language per CLAUDE.md Phase 8) — no second-language requirement exists yet. Trigger: a school or market actually requires a non-English UI.)
- [ ] Split global CSS into design tokens, component styles, and page/module styles when ownership or stylesheet size starts slowing changes. (Deferred: `styles.css` is large (~3,400+ lines) but has a single owner and is still organized with section comments; splitting now is a mechanical, regression-risky refactor for a problem (ownership contention) that doesn't exist yet with one developer. Trigger: a second developer regularly editing the same stylesheet, or the file growing enough that a specific change becomes hard to locate/land.)
- [ ] Instrument anonymous performance measures for scan-to-display latency, list response time, image load failures, and route bundle size. (Deferred: no analytics/observability backend exists to receive these measures yet, and there's no real school traffic to measure — instrumenting now means guessing at a metrics pipeline before it's needed. Trigger: first paying school pilot goes live, aligning with CLAUDE.md's Phase 8 pre-launch ops.)

## Definition of scalable for a new record surface

A new record surface is ready when it has tenant-scoped data access, bounded retrieval, stable ordering, loading/empty/error states, pagination or an explicitly documented bounded-preview limit, accessible create/edit behavior, responsive containment, and a clear path from preview content to the full collection.
